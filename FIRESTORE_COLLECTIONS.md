## `users`
Stores user account profile information (roles and departments are maintained in `memberships`).

- **Document ID**: Firebase Auth `uid`
- **Fields**:
  - `email`: string (User's email address) | **Default: from Auth**
  - `firstName`: string (Trimmed given names saved separately at signup; each word is title-cased while typing and before saving)
  - `surname`: string (Trimmed surname saved separately at signup, including compound surnames; each word is title-cased while typing and before saving)
  - `fullName`: string (Compatibility name in First name Surname order) | **Default: from Auth (or empty string)**
  - Name displays use Surname, First name when both separate fields exist, otherwise the saved fullName. Legacy accounts are not automatically split into name parts.
  - `isVerify`: boolean (Whether the user's email is verified) | **Default: from Auth**
  - `createdAt`: timestamp (Date the profile was created) | **Default: serverTimestamp()**
  - `updatedAt`: timestamp (Date the profile was last updated) | **Default: serverTimestamp()**
  - `profilePicture`: string (URL to the user's profile picture) | **Default: from Auth (or empty string)**
  - `isActive`: boolean (Whether the account is active) | **Default: true**

### `users/{userId}/notifications`
Stores notifications privately beneath the recipient's user document.

- **Document ID**: Firebase event ID, or a deterministic source-event ID for scheduled notifications
- **Fields**:
  - `title`: string (Notification heading)
  - `message`: string (Notification body)
  - `type`: string (Supported notification event type)
  - `isRead`: boolean (Whether the recipient has read the notification) | **Default: false**
  - `createdAt`: timestamp (Server timestamp used for ordering)
  - `sourceCollection`: string (Collection that produced the event)
  - `sourceId`: string (Source document ID)

### `users/{userId}/roomCommentReads`
Private per-user room comment read positions, synchronized across devices. Only the owning signed-in user can read or write these documents.

- **Document ID**: Room document ID
- **Fields**: `lastSeenAt`: timestamp of the newest committed comment loaded when the comments panel is closed; `seenComments`: optional map of individually clicked comment IDs to their creation timestamps (legacy documents without the map remain supported).
- Opening the panel preserves unread highlights. Each unread comment from another author has an amber highlight; clicking it or pressing Enter/Space marks only that exact comment seen. Closing/hiding the panel or closing Room Information advances the room read position and clears the remaining highlights. Bulk writes compact individually seen entries covered by the new timestamp. Transactions merge concurrent individual reads and preserve newer read positions.
- Clicked comments clear immediately in the current session while saving. Cached query results cannot temporarily reinstate notices; unread calculations wait for confirmed server snapshots. If saving fails, the panel offers retry and the current session still remembers what the user has seen.
- Buildings & Rooms shows a **New comments** badge on room cards and an amber dot on the comment toggle while another author's comment remains unread. With no read position, existing comments are unread. Own comments never trigger notices or highlights.
- The page subscribes to one latest-comment query per existing room (using the existing `roomId`/`createdAt` index), plus the current user's read-position collection. The query window doubles past own/individually seen comments until it finds unread feedback, reaches the room read position, or exhausts the room's comments. If the composite index is missing, the same room-only fallback as the comments panel is used. Comments remain stored in the top-level `comments` collection. Deploy the updated Firestore rules to allow the optional per-comment map.

### `departments/{departmentId}/courseWorkbooks/current`

Stores one complete editable courses workbook per department, independent of the schedule's school year/semester. `DepartmentCoursesWorkbook` loads this document when Manage Courses opens; an absent document starts with 50 empty rows.

- **Fields**: `schemaVersion: 1`, `encoding: 'gzip-base64'`, `data` (compressed workbook JSON), `jsonByteLength`, `departmentId`, `departmentCode`, `fileName`, `revision`, `generation`, `courseCount`, `membershipId`, `savedBy`, `createdAt`, `updatedAt`.
- The versioned workbook preserves every worksheet, cell value, blank row, source row ID, selected sheet, and all seven column widths. The six course headers are fixed in the component. Compressed data is limited to 900 KiB (50 MiB uncompressed); `data` is exempt from indexing.
- Accepted Admins, department Deans, and Program Heads can save. Each save stages its populated course rows, then a transaction checks fresh membership/department and the prior revision before publishing both workbook and row generation. Failed/stale saves do not replace the current workbook.

### `departments/{departmentId}/summaryWorkbooks/{academicYearId}_{semester}`

Stores the Summary tab's faculty load grid for one department and academic term. The blank DL Format follows the supplied `Summary.xlsx` headings and contains no faculty data. Import fills Faculty through the first Total (columns B–H) only; From Other Dept. through Overall Total and PREPS through OVERLOAD are excluded from imported grid values. Export writes its current values into that format. The Summary header's Auto Fill button reads saved `schedules` records for the department and term, groups faculty assignments, and fills Faculty, DEPT, Hours Lec/Lab, and their Total. Faculty names must resolve uniquely to a current accepted Instructor or Program Head in the department's member directory; the Faculty cells offer that directory and `TBA` as choices. Faculty names use title case while `TBA` stays uppercase. Reg/Prob/Cont cells offer Regular, Probationary, and Contractual; FT/PT cells offer FT and PT. A sole listed Lec or Lab instructor receives both hour types when the opposite Faculty cell is empty; distinct listed instructors receive only their respective hours. Parallel sections in the same saved group count once per instructor. Blank Lec/Lab Hours contribute `0`; flexible hours leave Total blank because their Lec/Lab split is unknown. The Hours Total column displays two decimal places, and Auto Fill saves its Total with two decimal places. Auto Fill updates matching faculty rows, uses blank rows or inserts rows for new faculty, and preserves other Summary columns. After filling, fully empty data rows move below populated rows without changing the row count or final total row. Auto Fill changes are undoable and are written to Firestore only when the shared workbook Save is used.

- **Fields**: `schemaVersion: 1`, `departmentId`, `academicYearId`, `semester` (`sem1` or `sem2`), `membershipId`, `savedBy`, `revision`, `state` (`rows`: an array of row maps containing `cells`, with 12 text cells per row and a final total row; `fileName`: XLSX name; `sourceData`: optional imported XLSX encoded as base64; `columnWidths`: 14 display widths including row count and blank separator), `createdAt`, `updatedAt`. Older saved 17-cell rows and 19 display widths are read by retaining only the Faculty through Overall Total range. Row maps keep Firestore from receiving unsupported nested arrays. The source preserves untouched formulas and auxiliary content on export when no rows are inserted or deleted.
- The shared workbook Save only writes Summary when its grid or filename changed. Accepted Admins and department Deans/Program Heads can edit and save Summary in any semester phase. Saves check that the academic year exists and verify membership and revision in a transaction to prevent stale overwrites. Signed-in users can read.

## `courses`

Each populated row of a saved courses workbook becomes a document. Empty rows remain in the workbook but do not create course documents.

- **Document ID**: `{generation}_{rowIndex}`; each save creates a new generation.
- **Fields**: `departmentId`, `departmentCode`, `sheetName`, `rowNumber` (source row ID), `session`, `semester`, `code`, `course`, `type`, `credits`, `sourceWorkbook` (`departments/{departmentId}/courseWorkbooks/current`), `generation`, `revision`, `membershipId`, `savedBy`, `createdAt`, `updatedAt`. Course cell values are preserved as strings, including credits, with a 64 KiB limit per cell.
- Consumers must read the workbook's current `generation` and filter course rows by that generation; `courseCount` records the expected populated-row count. Rows are staged in batches before the workbook is published, so unpublished or abandoned generations are ignored. After publication, rows of the previous generation are removed in batches. If cleanup fails, the saved workbook remains valid and the footer reports it.
- Authenticated users can read rows. Writes require an accepted Admin or the department's Dean/Program Head; published rows cannot be edited or deleted directly. Deploy the updated `firestore.rules` and `firestore.indexes.json` when applying the stricter local policy.

## `reservations`
Manages room reservation requests and their approval status.

Reservation review proceeds in order: department Dean recommendation, Registrar recommendation, then University Administrator approval or decline. A new request remains Pending after both recommendations; normal review moves it to Approved only after the University Administrator's final approval. The three boolean fields enforce the order transactionally, including when the status is changed through the callable. The Dean sees all requests for their department and can act first. The Registrar action becomes available after Dean recommendation. The University Administrator sees every reservation, but final decision actions become available only after both recommendations. Program Heads cannot access Manage Reservations or recommend requests. Admin sees all reservations and can manually set Pending, Approve, or Decline for the reservation's current review step through the callable. The step is inferred from the first recommendation that is not true and cannot be selected in the dialog. This writes the corresponding recommendation booleans, status, decline metadata, and audit event atomically; later steps are cleared when an earlier step is changed. Older open requests missing the booleans can complete the Dean and Registrar steps in this order. A legacy Pending request with a Registrar recommendation but no Dean recommendation returns to Registrar review after the Dean decides.

Recommendations save reviewer metadata and an atomic audit event, and notify the requester with booking_recommended. Each Dean recommendation also sends `booking_recommended` to accepted Registrars; each Registrar recommendation sends it to accepted University Administrators. Final approval sends `booking_approved` to the requester. Recommended requests retain their room interval, remain cancellable, expire like Pending requests, and are cancelled by conflicting class schedules. Registrar and Dean recommendation and decline buttons, including Approve and Decline in each role's status-edit modal, use Firestore transactions that check the current membership, department where applicable, and reservation; they write the recommendation or `Declined` status and required `declinedReason`, plus an audit event. Their status-edit modals offer Approve and Decline for open requests and requests declined by that role. Manually declining clears the reviewer's recommendation and any dependent recommendation flags. Reapproving a Registrar- or Dean-declined request restores Pending. Both clear decline metadata. The University Administrator's buttons and manual edit similarly offer Approve and Decline only after both recommendations. Standard final decisions use a client transaction to update `status`, `universityAdministratorRecommend`, decline metadata, and the audit event. A manual edit can decline an Approved request with a required reason or reapprove only a University Administrator-declined request, clearing its decline metadata. Extended approvals and reapprovals use `updateReservationStatus` for atomic room and schedule conflict validation; that callable must be deployed to make those actions available. A declined reviewer's icon is red; legacy declines without `declinedByRole` are inferred from the recommendation flags unless the request was auto-processed. Client transactions rely on the currently deployed permissive policy allowing writes to both `reservations` and `logs`; they will fail if the stricter local log rule is deployed. Deploy the updated updateReservationStatus and notifyReservationStatusChanged functions for the complete workflow. No new index is required. The existing permissive direct Firestore policy is unchanged: department filtering and callable authorization do not restrict arbitrary direct database access.

Each reviewer's manual status modal also offers Pending. It writes `status: "Pending"` and sets that reviewer's recommendation boolean to `false` without requiring a decline reason. Resetting the Dean also clears Registrar and University Administrator recommendations; resetting the Registrar also clears University Administrator approval. Resetting the University Administrator leaves both earlier recommendations intact. A reset from Declined clears the reason and decline metadata, and a reset from Approved reopens the request as Pending. The change and affected booleans are written with an audit event.

The Dean edit action is disabled once the Registrar has recommended or declined; the Registrar edit action is disabled once the University Administrator has approved or declined. The client transactions recheck the next role's decision before writing, including when an edit modal was opened before that decision.

- **Document ID**: Auto-generated ID
- **Fields**:
  - `roomId`: string (Reference to the room document ID)
  - `buildingId`: string (Reference to the building document ID)
  - `userId`: string (Reference to the user's UID)
  - `date`: string (Date of reservation, e.g., "2024-05-20")
  - `startTime`: string (e.g., "08:00")
  - `endTime`: string (e.g., "09:00")
  - `duration`: number (Duration in minutes)
  - `requestType`: string (`"Standard"` or `"Extended"`; missing values on legacy records are treated as Standard)
  - `extensionReason`: string (Legacy field; no longer collected, displayed, or required. Existing stored values are preserved.)
  - `purpose`: string (Required reason for new reservations; trimmed, maximum 50 characters)
  - `subjectCode`: string (Optional; trimmed and saved in uppercase, or an empty string when omitted. Reservation entries in ScheduleModal display N/A when empty.)
  - `classSection`: string (Optional; trimmed and saved in uppercase, e.g., "3BSIT - 1", or an empty string when omitted. Reservation entries in ScheduleModal display N/A when empty.)
  - `department`: string (Required for new reservations; automatically copied from the reserving user's membership, including the administrative or registrar office for those roles; read again during the reservation transaction)
  - `attendees`: number (Expected number of attendees)
  - `status`: string (`"Pending"`, `"Approved"`, `"Declined"`, `"Cancelled"`, or `"Completed"`) | **Default: "Pending"**
  - `registrarRecommend`: boolean (Whether a Registrar has recommended the reservation) | **Default: false for new reservations**
  - `deanRecommend`: boolean (Whether the department Dean has recommended the reservation before the Registrar) | **Default: false for new reservations**
  - `universityAdministratorRecommend`: boolean (Whether a University Administrator has approved the reservation after both recommendations) | **Default: false for new reservations**
  - `registrarRecommendedBy`: string (UID of the Registrar who recommended the request)
  - `registrarRecommendedAt`: timestamp (Server timestamp of the Registrar recommendation)
  - `recommendedBy`: string (Department reviewer's authenticated UID)
  - `recommendedByRole`: string (`"Dean"` for new recommendations; legacy records may contain `"Program Head"`)
  - `recommendedAt`: timestamp (Server timestamp of the recommendation)
  - `declinedReason`: string (Required, trimmed reason of 1–500 characters when a reviewer declines; also used by automatic expiration)
  - `declinedByRole`: string (Optional role of the reviewer who declined the reservation: `Registrar`, `Dean`, or `University Administrator`)
  - `declinedBy`: string (Optional UID of the reviewer who declined the reservation)
  - `declinedAt`: timestamp (Optional server timestamp of a reviewer decline)
  - `cancellationReason`: string (Optional; automatic cancellation explains that a class schedule occupies the reserved room/time)
  - `cancelledByScheduleId`: string (Optional reference to the saved schedule that caused automatic cancellation)
  - `cancelledAt`: timestamp (Optional automatic cancellation timestamp)
  - `autoProcessed`: boolean (Optional flag for automatic status changes)
  - `completedAt`: timestamp (Optional timestamp when an approved reservation concludes)
  - `evidencePath`: string (Firebase Storage path to one after-use room photo or video; absent until the requester submits proof)
  - `evidenceType`: string (`image` or `video`)
  - `evidenceFileName`: string (Original uploaded file name for display)
  - `evidenceSubmittedAt`: timestamp (Legacy single-file server submission time; displayed in Philippine time and preserved when more files are added)
  - `evidenceFiles`: array of `{ path, type, fileName, uploadedAt }` (Photo/video Storage paths, media types, original filenames, and Storage server creation times; new multi-file uploads append to this array)
  - `createdAt`: timestamp | **Default: serverTimestamp()**
  - `updatedAt`: timestamp | **Default: serverTimestamp()**

Completed reservations without either a legacy `evidencePath` or a saved `evidenceFiles` entry display **Needs Evidence** in My Reservations and Manage Reservations. The requester can upload up to ten JPG, PNG, WebP, MP4, WebM, or MOV files per submission (100 MiB per file) after the reservation is marked Completed, and can add more later. The client uploads to `reservation-evidence/{reservationId}/{uuid}.{extension}`, then transactionally checks ownership and current status before appending the files. Each new file carries its Storage server creation time in `uploadedAt`; the legacy `evidenceSubmittedAt` is preserved. Existing single-file evidence remains visible in a separate gallery. The upload dialog previews only newly selected media and lets the requester remove a selection. The requester can also remove saved evidence from the gallery; the client removes its reservation reference in a transaction, then deletes the Storage object. Deploy `storage.rules` to enforce upload ownership, type, size, and owner-only deletion; the existing deployed permissive storage policy does not enforce these restrictions until then.

Extended reservations cover one date within the room's operating hours and available days. The form uses start and end time pickers, bypassing only the standard maximum duration and 90-minute slot boundaries. Minimum duration, capacity, reservation date limits, the two-hour same-day submission lead time, and reservation/class conflicts remain enforced. Pending extended requests hold their selected interval just like standard requests. The room's current availability, hours, days, minimum duration, and capacity are read again during extended submission. Manage Reservations marks these bookings `EXTD` beside the time range; My Reservations, reservation details, and ScheduleModal (including its PDF output) label them Extended reservation. The calendar repeats the booking in each overlapping slot.

Before approving an Extended request, `updateReservationStatus` transactionally rereads the room, same-room reservations, schedules, and academic years. It rejects invalid times, events that already started (Philippine time), changed room constraints, overlapping Pending/Approved requests, and conflicting class meetings within their semester dates. A separate extension reason is not required; the form retains its required Purpose field for all bookings. Legacy split sessions and workbook meetings are included; unresolved class terms conservatively block overlapping approvals. Extended approval follows the same Registrar, Dean, and University Administrator review order. The Registrar may decline before recommending an open request and may manually cancel a Pending request; declines require `declinedReason`, which is saved with the reservation and audit event and shown to the requester. Deploy the updated `updateReservationStatus` callable to enable this server check; no new collection or index is required.

Saving a new schedule or changing its room, weekdays, times, academic year, or semester triggers `cancelReservationsForSchedule`. It cancels overlapping Pending/Approved reservations for the same room within the inclusive semester dates, considering every resolved workbook meeting and legacy split sessions. Saved Draft/Plot schedules take precedence; Returned/inactive schedules, expired reservations, terminal statuses, and adjacent time slots are excluded. Legacy academic years use their stored full-month boundaries when exact dates are absent. Missing/invalid/ambiguous terms are skipped. Paginated Firestore transactions recheck the current schedule, semester dates, and reservation status, making duplicate/out-of-order deliveries safe. Cancellation preserves the record and records its reason, timestamp, and schedule ID. The existing status-change notification includes the reason. This is asynchronous after Save and requires deployment of `cancelReservationsForSchedule` and `notifyReservationStatusChanged`; it does not backfill unchanged schedules or restore reservations when schedules are removed.

## `logs`
Append-only audit events. Manage Reservations uses the `updateReservationStatus` callable to atomically update a reservation and create one log per Registrar recommendation, Dean recommendation, or actual status change.

Schedules use `logDepartmentWorkbookSave`, an auth-context Firestore trigger on the canonical department semester manifest. Each meaningful committed workbook revision produces one `schedule.workbook_saved` event in category `Scheduling`. The manifest carries an optional version-1 `audit` summary in the same transaction as its sheet references and schedule projection. It contains the revision ID, previous revision, operation kind (`created`, `imported`, `updated`, or `repaired`), full change counts, up to 80 before/after descriptions (values limited to 400 characters), an omitted-description count, and whether a comparison baseline was available. The summary covers schedule additions, updates and removals; subject, faculty, room, time, day, year, section and status edits; cells, comments, notes, links, formatting, layout, schedule setup, and sheet additions/removals/renames/order. Selection-only saves produce no event. Unsaved changes and failed commits are not logged. Schedule update counts compare authored schedule fields such as room, faculty, meeting time/day, subject, section and status. Recalculated meeting references, validation results and parallel-group links still refresh in the schedule projection but do not count as member edits. Raw row values are already covered by workbook cell changes and are not duplicated as schedule field changes. One room-cell edit can therefore appear as one cell edited and one schedule updated, describing the same edit at two levels. Existing events retain their originally recorded counts.

Newer saves are loaded through the same verified cache/cloud loader and applied automatically when there are no local edits or active cell edits, resizing, or row/context menus. The current worksheet remains selected if it still exists. Unsaved changes are preserved; a notice offers **Merge and keep my edits** or **Discard edits and load latest**, and Save is disabled until the newer revision is resolved. Merge compares against the previous saved baseline, brings in other users' changes to untouched cells, year metadata and widths, and keeps local values for conflicts. The latest remote revision becomes the baseline and retained local edits remain unsaved. Incompatible row/year/worksheet layouts or a local replacement import block cell merging; an explicit **Keep my workbook** option retains the entire local draft against the latest revision for a subsequent replacement Save. Undoing local changes also permits automatic application. Own save acknowledgements are ignored; imports and saves pause delivery, and account/term changes or closing stop old listeners and discard late loads. Failed live loads keep the draft and offer Retry live updates. This synchronizes committed saves; unsaved typing is not shared.
- **Persistent workbook cache**: the complete saved workbook snapshot (all sheets, cell values/formulas, formatting, dimensions, hidden sheets, and schedule setup) is cached in IndexedDB, alongside the existing memory cache. It uses the bounded workbook-file cache (64 MiB memory / 150 MiB disk shared with legacy workbook files), isolated by Firebase project/app, account, and term. A single cache slot per account/term replaces older revisions after successful loads and saves, including empty saves and sheet deletions. Cache entries include the exact manifest revision/index, per-sheet generation signatures, cell-patch values, and sheet-text checksums. Before reuse, the loader fetches current server metadata and sheet parents, verifies the existence of every required chunk ID using bounded aggregate queries, and reads active cell edits. It rechecks the manifest and account before returning. Cache hits avoid downloading/decompressing large chunk payloads; live checks still require a connection. Missing sheet/chunk/cell documents retain the replacement-import workflow. Revision/generation/patch mismatches or corrupt/unavailable local storage fall back to verified cloud loading; server permission/network errors never fall back to cached data. Failed verification invalidates the local entry. Browser eviction or disabled IndexedDB affects performance only. Unsaved editor changes are not persisted in this cache.
- **Fast saves** use one transaction for changed snapshots or cells and the manifest. The transaction concurrently reads the current manifest, lock, year, and membership, checks the prior revision and semester permissions, and commits all changes together. The memory baseline scoped to the account, term, and revision avoids downloading snapshots again during subsequent saves and is rebuilt from a server-verified persistent snapshot after refresh. Preparation compares the full editor state locally; saving a small cell edit still validates/serializes the workbook but transmits only changed cell records and the manifest. The modal displays elapsed save time; console metrics report preparation, commit time, document counts, and estimated sheet/cell payload bytes (excluding manifest, lock, and protocol overhead).
- **Large-save fallback**: requests estimated above 4 MiB or touching more than six sheets use `.../workbooks/{schoolYear}/semesters/{semester}/saveLocks/current`. This reusable lease holds `status` (saving/idle), `saveId`, `savedBy`, `membershipId`, `academicYearId`, and `createdAt`, and expires after ten minutes. Up to four chunk writes run concurrently, then parent writes, then a transaction publishes the manifest and releases the lease. Cell edits are folded into snapshots for this path. Rules protect active slots and require either the matching atomic manifest commit or a fresh authorized lease. Failed staging preserves the previous complete workbook; stale/concurrent saves are rejected. Historical Storage manifests are checked for revision conflicts during migration.
- The `slots` maps in `sheets` and `chunks`, and `cells.text`/`cells.styleJson`, are exempt from indexing. `cells.baseRevisionId` remains indexed for the loader query. Deploy `firestore.rules`, `firestore.indexes.json`, and `storage.rules` before using these paths against the live project.
- Requests have a 90-second deadline and saves an eight-minute overall limit. Timeout/failure stops further publication. Lease cleanup waits at most three seconds; a late lease acknowledgement is released without resuming the cancelled save. A timed-out final commit may already have reached Firestore, so the UI asks users to reopen and check the saved version before retrying.
- A sheet, chunk, or active cell record deleted directly in Firestore permits authorized editors to import a replacement against the same term revision. Recovery rewrites the missing snapshots at stable paths and preserves creation time. Connection, permission, and malformed-data errors block saving.
- Excel import/export remains local to the browser. The retired test tab, copied modal, and test saving mode have been removed. Historical test documents and their security rules are retained; the application does not use them.
- **Parallel room connections**: sections sharing a valid PARALLEL meeting must use separate rooms that form a consecutive number chain in the same building and floor (for example PTC 300–301–302–303, in any section order). The validator resolves room IDs and code/name aliases against the rooms directory, uses its building/floor fields, and falls back to the room number's hundreds digit for legacy rooms without floor metadata. Different room-code prefixes/suffixes, gaps, repeated rooms and different buildings/floors produce a shared room-connection warning. TBA/unknown rooms retain their existing treatment while the known assigned rooms are checked. Lec/Lab and separate meeting slots are checked independently. Room recommendations also handle disconnected parallel assignments and offer only replacements that preserve a valid chain, while retaining normal availability and building-ranking rules.
- **Parallel validation during Plot**: PlotScheduleModal requires a resolved room for every section in the parallel meeting group before plotting, for both Registrar choices and provided-room approvals. Once at least one section has a resolved room, TBA, blank, unknown and deleted rooms produce a shared red completeness error listing the missing sections; a four-section group requires all four rooms. Completely unassigned groups show no completeness error until the first room is chosen. It also applies the workbook's connection validator to saved and staged rooms, highlighting invalid groups and showing errors in the tooltip and footer. The Plot transaction rereads assigned peer rooms from current same-term schedules and validates the complete proposed group before any writes; partially assigned or disconnected groups cannot be approved or saved with changed rooms. All required room selections can be staged and committed together. Returning an unchanged provided assignment to Draft remains allowed, and unrelated invalid groups do not block other schedules. No new collection or index is introduced.
- **Parallel group checkbox**: PlotScheduleModal places one checkbox at the card's top right for a parallel group, instead of a checkbox beside each room. Group size comes from the actual matching schedules, including groups of one, two or three; checkbox eligibility, room-chain recommendations and atomic saves do not assume four members. A single parallel schedule needs one resolved room and no adjacent peer. It remains unchecked and disabled for incomplete or disconnected rooms. Assigning rooms, including a recommended chain, does not check it automatically: the user must check the completed group manually before clicking Plot. Room edits clear staged approval for that group, retaining room choices. Unchecking an unsaved Draft group's approval cancels approval and keeps those choices pending. Local `PlotAssignment.parallelGroupKey` tracks this approval requirement across all sections and undo/redo; it is not persisted to Firestore. Plot is disabled while any parallel room changes await manual approval, and the service rejects parallel requests without an explicit target status. Toggling stages the whole group's status in one history entry. Plot expands explicitly approved parallel room/status saves to all matching same-term member rows with revision checks, preserves provided room text, and commits one shared Draft/Plot status atomically. Non-parallel provided-room checkboxes also appear at the top right.
- **Instructor overlap recommendations**: editing a conflicted Lec/Lab Time or Day cell shows all valid Recommended whole-cell alternatives, without a count limit. Only entries with an instructor overlap may change; clear time entries and individual weekdays remain fixed in their original positions. Time suggestions preserve each meeting's duration, keep current days, and try half-hour starts within the calendar's standard 07:30–18:00 day, favoring the fewest and nearest changes. Day suggestions keep current times and preserve one or two day entries, including positional days for split meetings. Both check the canonical instructor and assigned-room overlap rules across every workbook sheet, the row's other Lec/Lab meetings, and PARALLEL groups. Selecting a recommendation uses the existing cell edit and undo flow; other cells stay unchanged. No alternatives appear for malformed input, room-only conflicts, or when no safe option exists. Like room recommendations, this checks the open workbook rather than other departments' schedules or personal availability.
- **Room dropdown recommendations**: an overlapping or TBA compact schedule room entry with valid days and times offers available rooms from every building with recorded room use in the workbook (or the previous term when the workbook has no assigned rooms), labeled Recommended. There is no room-count limit per used building or limit on valid parallel room chains. Usage counts each schedule row once per building across all sheets; Lec/Lab or repeated meetings in that building do not inflate its count. Buildings sort by usage descending, with building ID as a stable tie-breaker, and rooms sort by name within each building. Buildings without recorded room use do not contribute recommendations. Availability uses the canonical overlap and PARALLEL rules against all meetings in the open workbook's sheets, including hidden years, Lec/Lab, resource aliases and both slash-separated meetings. Saved Draft and Plot meetings with assigned rooms from other departments in the selected term also trigger alternatives and exclude occupied rooms from ordinary and parallel recommendations. A shared room or a selection replacing both room entries must be free for every affected meeting. Ambiguous room names are excluded. Plot uses the same candidate rules and workbook room-cell grouping for editable saved schedules, so equal saved inputs produce equal recommendations. The dropdown retains ordinary room filtering and its existing cell-matched width. Recommendations do not query reservations or other departments' unpublished workbooks.

### Legacy Storage-backed workbooks (migration input)

- **Document path**: `departments/{departmentId}/workbooks/{schoolYear}/semesters/{semester}`.
- Each department, school year, and semester has an independent workbook.
- **Fields**:
  - `schemaVersion`: number (currently `1`).
  - `departmentId`, `departmentCode`, `academicYearId`, `academicYear`, `semester`: string.
  - `fileName`: string (original imported `.xlsx` filename).
  - `workbookPath`: string (Firebase Storage path to the original `.xlsx`).
  - `editorStatePath`: string (Firebase Storage path to the current editor JSON snapshot).
    - `ScheduleSetup.statusColumn` stores the physical zero-based column index for Status, immediately after F2F Room when initialized (for example W after V). It uses normal worksheet selection, formatting and borders, while its text is computed and protected. Save/export include the Status header and Draft/Plot values in actual XLSX cells. Old display-only Status formatting is migrated into normal `cellStyleOverrides`; data and formatting to its right shift one column. Validation colors also highlight Status and temporarily override its custom fill.
  - `revision`: positive integer, incremented on save.
  - `revisionId`, `savedBy`, `membershipId`: string.
  - `createdAt`, `updatedAt`: timestamp.
- **Storage files**: new saves use `department-workbooks/{departmentId}/{schoolYear}/{semester}/semesters/{revisionId}/{original.xlsx|editor.json}`. Previous uploads under `department-workbooks/.../{schoolYear}/.../workbooks/` and both historical `department-workbooks/.../{schoolYear}/.../revisions/` and `department-workbooks/.../{academicYearId}/.../revisions/` remain readable. The distinct new segment lets Storage rules check the new upload grant and academic year within their two-document lookup limit. Subsequent saves reuse the original XLSX unless replacing missing files; editor snapshots have a new revision path.
- **Upload grants**: `.../workbooks/{schoolYear}/semesters/{semester}/uploads/{revisionId}` holds `savedBy`, `membershipId`, `academicYearId`, and `createdAt`. Grants are immutable and authorize staging for ten minutes. Failed saves remove their staging objects and then their grant when cleanup succeeds. A committed workbook retains its grant.
- **Schedule rows**: saving this modal synchronizes only rows with its `sourceWorkbook`. New and historical manifest paths are queried during migration; deterministic row IDs keep their existing creation timestamps. Rows and the manifest commit together, and removed workbook rows are deleted. Other terms and unrelated rows are retained.
- **Permissions**: accepted Admin members can save during Drafting, Plotting, Revision, or Final. Accepted Dean/Program Head members can save their own department during Drafting or Revision. Registrar department workbooks are read-only in every phase; the UI hides Save and the toolbox, blocks Ctrl/Cmd+S, and exposes only View comments in each sheet's options. Viewing remains available for all phases. Workbook services reject Registrar saves independently of the UI. Registrar room plotting has a separate permission check and remains available in Drafting, Plotting, Revision, or Final. The local `canSaveWorkbook` Firestore rule excludes Registrar; deploying it is necessary for server enforcement, and the existing deployed-policy note still applies. Rules check the main `academicYears` document and membership. Stale revisions cannot overwrite newer saves. Signed-in readers can open saved workbooks; missing objects prompt an authorized replacement import without resetting the revision. The deprecated Schedule Setup dropdown is removed from the toolbox; saved legacy setup metadata remains readable.
- Opening first verifies server metadata and object generations. Cached original/snapshot files are scoped to project, bucket, and account. Access, deletions, and changed generations are rechecked before using the cached files.
